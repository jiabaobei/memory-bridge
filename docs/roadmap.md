## GitNexus 借鉴版 ✅（v0.14.0，2026-08-31，图谱结构强化）

对照 GitNexus（abhigyanpatwari/GitNexus，零服务器代码知识图谱引擎）做的
克制借鉴。事前核对的关键发现：**记忆桥 v0.9 已实现三路混合检索 + RRF
融合 + SAN 一跳扩展**（GraphRAG Local Search 的极简版），所以差距不在
「有没有图谱」而在「边从哪来、可不可信」——GitNexus 的边来自 AST 的
确定性，记忆桥的边来自字符 n-gram 共现的统计代理。

借鉴了什么（都落在结构层，不碰记忆内容）：

- **确定性关系源 → 实体锚点**：吸收其「图谱的价值在关系确定」的思路，
  但降级实现——不解析 AST，只用零依赖正则抽原文中确凿存在的符号
  （代码符号 / 文件路径 / owner-repo / 全大写代号 / 用户标签），
  共享同一锚点即连 entity 边
- **类型化边 + 证据**：边带 `kind`（semantic / cooccur / entity）与极短
  `evidence`，每条边可回答「为什么相关」
- **社区划分 → 整簇预加载**：吸收其 Leiden 社区检测的思路，用并查集
  连通分量（零依赖）把记忆切簇，`preload --cluster` 整簇加载
- **溯源引用 → 召回理由**：吸收其 `[[file:line]]` 溯源思路，context
  注入标注极短命中路径（向量 / 关键词 / 图谱）

明确不借：

- ❌ 图数据库（KuzuDB / LadybugDB / Neo4j）：破坏「一个 SQLite 文件带走」
  的核心卖点
- ❌ Tree-sitter 全量 AST：记忆是自然语言不是代码，且原生依赖违背
  核心零依赖
- ❌ PDG 程序依赖图 / 污点分析：代码专属，记忆层没有执行语义
- ❌ PostToolUse 提交后自动重索引：违背内容冻结；记忆桥只增不改，
  本就没有 stale index 问题——这是优势不是短板
- ❌ 为 temporal / device / scene 建边：会让图从稀疏变爆炸（同设备
  所有记忆两两连边 = O(n²)），违背论文 edge density < 0.1% 的设定；
  这些仍走节点元数据 + v0.13.1 的 `scope` 范围过滤

三原则守护：省 token（理由每行 ≤8 字符、evidence 不进上下文、边类型
收敛 3 种）；简洁（零新依赖、零新文件，实体抽取并入 san.py、聚类并入
heat.py，唯一新开关 `preload --cluster`）；内容冻结（只加结构/元数据）。

测试：83 项与 v0.13.2 基线**完全一致**（79 通过 / 4 失败为环境相关遗留），
零回归。

## MoNe 背书版 ✅（v0.13.2，2026-08-31，纯文档）

对照高通 MoNe（Modular Neural Memory，ICML 2026 AdaptFM Workshop）做的
路线核对。结论：**零代码借鉴，纯叙事背书**。

核对结果：

- MoNe 的四条机制与记忆桥全部同构且已具备：骨干冻结 ≈ 内容冻结；
  写入一次多查询重读 ≈ 外置记忆本职；增量续写不重处理旧内容 ≈
  v0.8 增量建边 + DSS 增量差分；固定记忆预算 ≈ v0.9 预算注入
- ❌ 参数态记忆路线本身不借：把历史写进权重 = 难审计、难精确删除、
  隐私边界难保证（Metis 已自认），与内容冻结 / 可搬运可加密 / 零依赖
  三原则全部相悖；且 MoNe 需 LoRA 离线训练，是训练框架不是记忆层
- [x] 中英 README「领域收敛」补**第六数据点**：连参数派都在实践
  「冻结本体 + 外挂记忆」——冻结是两派共同的纪律，区别只在冻什么：
  他们冻模型，我们冻内容

测试：无代码改动，83 项不变

## Context7 借鉴版 ✅（v0.13.1，2026-08-31，小修订）

对照 Context7（upstash，「最新文档直接注入 prompt」，6 万+ 星）做的取舍式
借鉴。核心结论：**它对记忆桥的验证意义大于借鉴意义**——其三大机制
（生成时按需注入 / token 预算控制 / 常驻触发规则）记忆桥在 v0.9/v0.10
已具备（Path A / 预算注入 + 沉默契约 / recall-hint），且沉默契约比它更细。
真正值得借的只有它两段式检索里的一条洞察。

借的：

- [x] **「已知目标直达」**（Context7 斜杠语法 `use library /supabase/supabase`：
      调用方已知目标就跳过模糊匹配）→ 检索加**可选** `scope` 范围直达：
      `tag:<名>` / `scene:<名>` / `kind:<fact|procedure>`，指定时先过滤候选
      再走三路融合。CLI `search/context --scope` + MCP `memory_search(scope=)`。
      纯只读过滤（读元数据），不碰记忆内容；不传行为完全不变；未知字段
      静默不过滤
- [x] 配套约定：**指定范围后无命中不记缺口**（范围内没有是预期，不是记忆
      缺失，避免缺口提醒噪声）

明确不借的（违背三原则 / 初衷）：

- ❌ 云端托管索引 + API key + 限流——与「自持通道、网盘只见密文」隐私叙事
      正面对撞（Context7 后端闭源、中心索引）
- ❌ 爬取外部内容入库——记忆只来自用户显式写入，爬内容进来等于给幻觉开
      进库通道，违反内容冻结的写入纪律
- ❌ SDK / CLI / npm 多包生态——违反零依赖极简

设计判断：Context7 用 6 万星验证了「生成时注入外部知识 + 预算 + 常驻提醒」
这条路线的市场价值——这与记忆桥的路线同构，是外部背书而非要追赶的差距。

测试：80 → 83 项（新增 scope 过滤 / kind 直达 / 范围未命中不记缺口 3 例）

## 通道归一版 ✅（v0.13.0，2026-08-31）

用户反馈驱动：PC 与笔记本已通过 OneDrive 通道共享记忆，但项目此前**只有
「每台设备各自选云盘」的规则，没有「所有设备指向同一通道」的保证机制**。
真实分裂路径：设备 A 装了坚果云 + OneDrive（规则选中坚果云）、设备 B 只有
OneDrive（选中 OneDrive）——两台设备静默指向两个云，没有任何警告。

- [x] **通道身份证 `channel.json`**：首个发布/初始化的设备在通道目录落
      自描述清单（通道 ID / 创建者 / 时间 / 嵌入器指纹）。纯元数据——
      **不含口令、不含任何记忆内容**，内容冻结不受影响；先写临时文件再
      改名，与差分包同一套半包防御
- [x] **自动认领（adopt）**：后续设备首次 publish / fetch / init 时认领
      既有通道的 ID；init 明确输出「已加入既有通道（由某设备创建）」
- [x] **分裂显式告警**：本机通道 ID 与云盘身份证不一致 → `channel` /
      `doctor` / `publish` / `fetch` / 自动同步全部显式 ⚠️；先到先得，
      身份证绝不被后来者改写；修正后告警自动清除
- [x] **`membridge channel` 一致性体检**：本机通道 / 身份证 / 通道里出现
      过的其他设备（纯元数据，解析自差分包文件名）
- [x] **OneDrive 多根目录识别**：家目录下所有 `OneDrive*` 根——同一云盘
      在不同设备上的根目录名常常不同（`OneDrive - 个人` / `OneDrive - 公司`），
      此前只匹配 `~/OneDrive` 会漏检
- [x] doctor 通道健康：通道目录不存在（云盘未登录 / 未开同步 / 路径变更）
      与通道分裂两类告警

设计判断：通道一致性是**元数据问题，不是内容问题**——与嵌入器指纹握手
（保证两端"语义一致"）互补，身份证保证的是两端"指向同一个地方"。手机 /
平板走网关基站模式，本来就不持有通道，不受影响。

测试：新增 `test_channel.py` 8 项；72 → 80 项

## 移动端接入版 ✅（v0.11.0，2026-08-31）

手机与平板无法复用「网盘差分包」模型（网盘 App 没有本地同步文件夹；
iOS 跑不了 Python），本版给出两条分开的路线，详见
[docs/mobile.md](mobile.md)：

- [x] **路线 A「瘦客户端 + 基站」**：`membridge gateway`（纯标准库
      http.server，零新依赖）。手机不持有完整记忆库，经口令保护的
      HTTP 读写家里常开设备上的库——移动端日常只需要 Add / Search /
      Preload 三个动作。内置随身记网页；`/add` `/search` `/preload`
      接口供 iOS 快捷指令与任意客户端直连；跨网推荐 Tailscale 自持
      组网，支持 --cert/--key TLS，绝不开公网明文端口。写入管线与
      `memory_add` 完全一致——内容冻结无任何例外
- [x] **路线 B「Android 完整节点」**（文档方案）：Termux 跑完整
      membridge，rclone 挂网盘目录做差分包通道，crond 定时——手机
      作为平等节点，离线可用
- 设计判断：路线 A 其实是 Phase 2「自托管中继」的轻量先行形态——
      中继不是独立服务，就是你自己家里那台 PC

遗留：iOS 原生 App / Android 原生 App（若做）都定位为路线 A 的
客户端壳，不引入新协议。

## memU 借鉴版 ✅（v0.10.0，2026-08-31）

对照开源竞品 memU（NevaMind-AI，Apache-2.0，「个人记忆存成 Wiki」）做的
**取舍式借鉴**——它是直接竞品，所以逐项过三原则后只借两样：

借的：

- [x] **「记忆就是文件」的可审计性** → `membridge export`：整座库渲染为
      Markdown（场景域分组 + fact/procedure 分节 + 设备/时间出处）。
      与 memU 的路线分歧在出口方向：**只读视图，永不回写**——手改导出
      文件不会、也无法流回库，内容冻结承诺多一个人人可验证的出口
- [x] **inject 缝（常驻召回指令）** → `membridge recall-hint`：打印一行
      提示由用户自愿粘贴进 CLAUDE.md / AGENTS.md。memU 由安装器代写宿主
      指令文件；我们只打印不代写（极度简化 + 不碰用户环境）

明确不借的：

- ❌ **Agent 自动蒸馏管线**（定时读会话日志 → LLM 蒸馏 → 自动入库）：
      记忆内容由 LLM 生成，幻觉从此有进库通道，与内容冻结相悖。写入
      主动权保留在明面上的 `memory_add`；经验沉淀走人工/Agent 显式写
      `kind=procedure` 的约定（README 已写明）
- ❌ 云托管同步（memu.so）：与「端到端加密、网盘只见密文」的自持隐私
      叙事正面对撞
- ❌ 500 行极简核心的形态对标：记忆桥的核心价值在跨设备同步与隐私
      分级，复杂度花在 DSS/PAMS 上是值得的

遗留的争议问题（诚实记录）：memU 的 ADR 明确论证「不做多跳图遍历，
图结构的收益配不上复杂度」。我们 v0.9 的 SAN 一跳图路恰好是中间位
（一跳、零参数、成本极低），暂保留——但 **Phase 4 UEP 必须用数据回答
图路增益**（见下）。

## 借鉴版 ✅（v0.9.0，2026-08-31）

对照三份外部研究做的集中借鉴。三条产品原则的对照检查：**内容冻结**——
全部改动只落在检索 / 注入 / 调度层，截断注入只取原文连续片段；**极度省
token**——预算注入、沉默契约、工具描述瘦身全部指向 token 开销；**极度
简化易上手**——无新命令（能力并入既有 search / context / doctor）、无新
必填参数、核心保持零依赖。

借鉴清单（来源 → 落位）：

- [x] 三路混合检索 + RRF 融合（Knowledge OS：Wiki-RAG + GraphRAG 实践）
      → 新模块 `retrieval.py`，CLI 与 MCP 检索全部切换
- [x] 缺口发现（Knowledge OS「检索即更新」的安全子集：只记元数据、只提醒，
      内容永远由用户写）→ `store.record_gap` + `doctor` 显示
- [x] 预算注入 + 超额截断（Metis：查询时只读约 56 token 而不重放 1410；
      airllm：只载入当前这一步需要的层）→ `injection.serialize` 预算填充，
      超预算条目注入原文前缀（截断 ≠ 改写，内容冻结无损）
- [x] 沉默契约（Meta Proactive Memory Agent：沉默也是动作）→ 无高置信命中
      时显式返回「本轮不干预」，不硬凑弱命中
- [x] 工具描述瘦身（Perplexity Portable Computer 的上下文纪律）→ MCP 三个
      工具描述各压缩到一行，是 v0.8「工具面 4→3」之后的第二步
- [x] 可选 `kind` 标注（Proactive Memory Agent 记忆三分法取其二：
      fact / procedure；私有进度类不进库）→ `add --kind` / `memory_add(kind=)`，

- ❌ 摘要 / 改写式记忆处理（GraphRAG 社区摘要、Metis 参数态压缩写入）

- ❌ 五层企业架构（Qdrant + PostgreSQL + Redis + MinIO + 编排框架）
      ——违反单文件零依赖与极简哲学
- ❌ 全量记忆常驻暴露（Proactive Memory Agent 消融证明全量暴露反而更差）
      ——违反省 token

README / README_EN 新增「领域收敛」章节，引用 Metis
（arXiv 2607.26760）、Proactive Memory Agent（arXiv 2607.08716）与
Perplexity Portable Computer 作为外置记忆路线的背书。测试 51 → 59 项。
